# Search Algorithms on OpenStreetMap: Bidirectional Dijkstra, A* and Hill Climbing

An interactive, place-agnostic Jupyter notebook that runs **three search algorithms** (Bidirectional Dijkstra, A\* and Hill Climbing) on a real street network downloaded from OpenStreetMap, animates them, measures them, and writes a complete lab report.

| File | What it is |
|---|---|
| `dijkstra_osm_visualizer.ipynb` | The project. Pipeline + the three algorithms + the lab report (Design, Implementation, Result) with live outputs. |
| `RESULTS.md` | The full lab-report results (tables, figures, analysis). Generated by the last cell of the notebook. |
| `results/` | All report figures (`fig01_...png` to `fig14_...png`) and interface screenshots. |
| `exports/` | Per-algorithm animation: `.json` data, standalone `.html` viewer, `.mp4` video. |
| `osm_cache/` | Cached maps, so reruns work offline. |

## The problem all three algorithms solve

The map is a graph: every **intersection is a state**, every **street segment is an action** whose **cost is its length in metres**. Given a start intersection **A** and a goal intersection **B** (random but seeded, at least half the map diagonal apart), find a route from A to B.

The notebook converts the OSM graph into plain adjacency lists (`adj[u] = [(v, length_m), ...]`) plus node coordinates in metres. For the backward search it also builds the **reversed adjacency** (`radj[v] = [(u, length_m), ...]`: the streets that *enter* `v`). All algorithms share the same signature `fn(problem, source, target, trace) -> SearchResult` and are registered in an `ALGORITHMS` dictionary. When a `trace` is passed, the algorithm records *which node it expanded, on which side (forward or backward) and which streets it looked at*; the animation and the figures are drawn from that record only.

## How each algorithm works, step by step

### 1. Bidirectional Dijkstra (uninformed, optimal)

Plain Dijkstra spreads out from A like one big ripple until it touches B. Bidirectional Dijkstra starts **two ripples**: a *forward wave* from A and a *backward wave* from B. Each wave only has to travel about half the distance, and two small circles cover much less area than one big circle. It does not use any heuristic; it simply meets in the middle.

1. **Two searches.** The forward search starts at A and follows streets normally (`gF[A] = 0`). The backward search starts at B and follows streets **in reverse** using `radj` (`gB[B] = 0`). Each has its own priority queue (a binary heap, its *frontier*) ordered by distance from its own root, its own distance array, `prev` array and set of settled nodes.
2. **Keep a record of the best route.** `best = infinity` is the cheapest A-to-B cost found so far and `meeting` is the intersection it passes through.
3. **Stop rule.** Before each step, compare `top(forwardFrontier) + top(backwardFrontier)` with `best`. If the sum is at least `best`, the waves have provably met and no shorter route can exist, so stop.
4. **Pick a side.** Advance the search whose top entry is smaller. This keeps both waves at the same radius.
5. **Settle a node.** Pop `(d, u)` from that frontier; skip it if `u` was already settled on this side (a *stale* heap entry). Otherwise settle `u`.
6. **Relax its streets.** Forward side: look at the streets leaving `u`. Backward side: look at the streets entering `u`. For each neighbour `v` with street length `w`, if `d + w` is better than that side's best-known distance to `v`, store it, remember `prev[v] = u` and push `v` into that frontier.
7. **Update the meeting point.** Whenever a node `v` has been reached by *both* waves, `gF[v] + gB[v]` is the cost of a full route A -> v -> B. If it beats `best`, record it and remember `meeting = v`.
8. **Build the path.** Follow the forward `prev` pointers from `meeting` back to A, and the backward pointers from `meeting` forward to B, and join the two halves.

*Result on the default instance:* **257 nodes expanded** (143 by the forward wave, 114 by the backward wave) and the optimal 2,426.5 m path. In the animation the blue wave grows from A, the purple wave grows from B, and they touch in the middle.

### 2. A* (informed, optimal)

A* is **one** best-first search from A to B, ordered by **f(n) = g(n) + h(n)**.

* `g(n)`: real cost already travelled from A to `n`.
* `h(n)`: the **heuristic**, the straight-line distance in metres from `n` to B (computed from the projected coordinates by `euclidean_heuristic`).

Step by step:

1. Compute `h` for every node (one vector operation). Set `g[A] = 0` and push A with priority `f = 0 + h(A)`.
2. Pop the node with the smallest **f**. Streets that lead towards B have a small `h`, so they win over streets that lead away from B, even if those are slightly cheaper so far.
3. If it is B, stop and rebuild the path through `prev`.
4. Otherwise expand it: for each street `u -> v` of length `w`, if `g[u] + w` is better than the best known `g[v]`, update `g[v]` and `prev[v]` and push `v` with priority `g[v] + h(v)`. A node that was already expanded is allowed to be re-opened if a cheaper route to it is found, which keeps A* optimal even when the heuristic has tiny numerical inconsistencies.

Because a street is never shorter than the straight line, `h` never overestimates (it is *admissible*), so the first time A* pops B the path is optimal. The notebook measures this: `h` is on or below the true remaining distance for every node (`results/fig08_heuristic.png`).

*Result on the default instance:* **164 nodes expanded** for the same optimal path. The explored region is a narrow band from A towards B.

### 3. Hill Climbing (informed, local search, not optimal)

Hill climbing keeps **no frontier and no memory**. It only stands on one intersection and looks at its neighbours.

1. Start at `current = A`.
2. If `current` is B, stop with success.
3. Look at **all neighbours** of `current` and compute `h(v)` (straight-line distance to B) for each.
4. Choose the neighbour with the smallest `h` (steepest ascent: the "hill" is *closeness to B*).
5. If that best neighbour is **not strictly closer** to B than `current`, stop with **failure**: this is a *local optimum* (a dead end, a wall, a street that first has to lead away from B).
6. Otherwise move there, add the street length to the cost and go back to step 2.

It is extremely cheap (a handful of expansions, one node of memory) but it is neither complete nor optimal. On the default instance it stops after only 6 nodes, about 630 m of walking, still far from B. Over 200 random pairs it reaches B only in a small minority of cases (see `RESULTS.md` for the exact rate).

### Side-by-side

| | Bidirectional Dijkstra | A* | Hill Climbing |
|---|---|---|---|
| Frontier | two min-heaps on `g` (forward + backward) | one min-heap on `g + h` | none (one current node) |
| Looks at the goal? | yes, starts a second wave there | yes, via `h` | yes, via `h` |
| Needs a heuristic? | no | yes | yes |
| Always finds a path? | yes | yes | no |
| Shortest path? | yes | yes | no |
| Memory | O(V) | O(V) | O(1) |

## Features

- **Place-agnostic**: change `PLACE` to any town. Download, scaling and animation need no hard-coded parameters. If a polygon fails to geocode or is too large, it falls back to a radius and shrinks until the graph fits `MAX_NODES`.
- **Algorithm registry**: add another algorithm by writing a function with the shared signature and calling `register_algorithm(...)`.
- **Validated**: Bidirectional Dijkstra and A* are checked against `networkx.shortest_path_length` (on the main instance and on every random pair of the statistical comparison); Hill Climbing is checked to be a real walk that never beats the optimum.
- **Animation**: zero-dependency HTML5 canvas viewer embedded in the notebook (and as standalone `.html`), plus an `.mp4` fallback for viewers that block JavaScript. For Bidirectional Dijkstra the forward wave is blue and the backward wave is purple.
